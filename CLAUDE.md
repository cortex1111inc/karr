# Vanspire OS

CRM/lead-management/retention/billing platform for car rental and service businesses. See `README.md` for setup, stack, and project structure — read it before making structural changes.

Quick facts an agent needs before editing:

- **Multi-tenant.** Every table except `organizations` has `orgId`. Every query must scope to `requireUser().orgId` — never trust a client-supplied org/customer/lead ID without also filtering by it.
- **Data layer is server-only.** Server Components fetch with Drizzle directly; mutations are Server Actions in each feature's `actions.ts`. Don't add API routes for CRUD.
- **File convention is `proxy.ts`, not `middleware.ts`** (Next.js 16 renamed it — see AGENTS.md above). Don't reintroduce a `middleware.ts`.
- `npm run db:push` crashes against this project's Supabase instance (a drizzle-kit introspection bug, unrelated to schema content). Schema changes go through hand-written SQL instead — see `db/MIGRATIONS.md` before touching `db/schema.ts`. Confirm with the user before applying any schema-changing SQL to a real (non-empty) database.
- Direct `postgres`/Supabase connections from this network occasionally throw `ECONNRESET` on the first attempt (confirmed transient — retry succeeds). Don't treat a single `ECONNRESET` as a code bug; retry once before investigating further.
- **Public routes are the exception.** Only `/login`, `/book/[slug]`, `/status/[token]`, `/quote/[token]`, `/invoice/[token]`, `/api/cron/*` bypass the auth gate (`lib/supabase/proxy.ts` → `PUBLIC_PATHS`). Never fetch or mutate org data on a public route without scoping through the resource's own lookup key (org slug, lead/quotation/invoice public token) — there's no `requireUser()` to fall back on there.
- **Money is `numeric`, never float, and computed once.** `lib/billing/money.ts#calculateTotals()` is the only place subtotal/tax/total get computed — call it server-side, store the result, never re-derive totals from line items in a component or on every read. Same for document numbers: always go through `lib/billing/numbering.ts#nextDocumentNumber()` (one atomic `UPDATE ... RETURNING`), never `count(*) + 1` (races under concurrent writes).
- **Invoice `status` is derived, not set.** `draft`/`sent` are manual; `partial`/`paid` are computed from `amountPaid` vs `total` every time a payment is recorded/removed (see `app/(app)/invoices/actions.ts`). Don't add a form control that lets someone pick "paid" directly — record a payment instead.
- **Outbound WhatsApp always goes through `lib/whatsapp/sendWhatsApp()`**, never a direct fetch to Meta's API from feature code — it's what keeps every send audited in `whatsapp_messages` and keeps the app working without live credentials (console fallback). Follow the same provider-interface pattern for any other external channel (SMS, email) added later.
- **Third-party credentials go in the `integrations` table via `/integrations`, not env vars.** Env vars (`WHATSAPP_*`) are only the shared fallback when no org has connected its own. New integration = new row type there, encrypted with `lib/crypto.ts` (`encryptSecret`/`decryptSecret`) before it touches the DB — never store a raw token/secret in a text column, and never echo a saved secret back to the client (the form only accepts a replacement, never displays the old value).
- **Vehicles and stock items are separate features, not one "inventory."** Don't merge them into a shared table even if a task description says "inventory" — a vehicle's fleet-status model (`available`/`rented`/`maintenance`/`retired`) and a stock item's quantity model (`quantityOnHand`/`lowStockThreshold`) don't unify cleanly, and forcing them into one table was already considered and rejected (see `ROADMAP.md` Phase 4).
- **Never mutate `stockItems.quantityOnHand` directly.** Every change goes through `recordStockMovement()` (`app/(app)/inventory/actions.ts`), which writes a `stock_movements` row *and* updates the count in the same action — direct updates break the audit trail.
- **"Conversion" in `/reports` means `stage = 'booked'` right now**, for leads *created* in the selected range — not a true point-in-time funnel. Know this before trusting or extending the numbers: a lead created outside the range that converted inside it isn't counted, and one created inside that converts later shows as converted retroactively once viewed. Fine as a trend signal, not precise history — don't present it as more exact than that without adding a stage-change-history table first.
- **Reports aggregation is done in JS, not SQL `GROUP BY`.** Deliberate at this data scale — fetch the date-range rows once, aggregate with `Map`s in the page component. Don't "fix" this into raw SQL aggregation unless row counts actually justify it; it just adds complexity for no measured benefit today.
- **CSV export ignores date filters on purpose** (`app/api/export/*`) — it's a full-data escape hatch (backup/spreadsheet/accountant handoff), not a filtered report. Don't wire the `/reports` date-range picker into it without the user asking for that specifically.
- Design tokens (colors, fonts) live in `app/globals.css` under `@theme inline` — extend there, don't hardcode hex values in components.
